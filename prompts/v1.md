# Task: 3D Gaussian Splatting reconstruction web app

I'm attaching a small set of photographs (typically 3–6) of the same scene or object, taken from different viewpoints. **No camera poses or intrinsics are provided.**

Build a deployable web app that performs an **end-to-end 3D Gaussian Splatting (3DGS) reconstruction** from these images and lets a viewer orbit around the result interactively in the browser.

## Deliverable

A single web app that:

1. Runs entirely in the browser preview (no separate backend service required to be reachable).
2. Either consumes the attached images at build time or lets the user upload them at runtime — your choice, but the deployed app must work with the attached images out of the box.
3. Displays the reconstructed scene as 3D Gaussian splats, rendered live from the user's chosen viewpoint.
4. Provides **orbit controls**: mouse drag to rotate around the scene, scroll wheel to zoom, right-click drag (or modifier+drag) to pan.
5. Shows a **status / progress indicator** while reconstruction is happening (3DGS pipelines take seconds to minutes — silent freezes are unacceptable).
6. Includes a **visible on-screen text panel** (collapsible is fine) that states: which approach you took, which libraries handled which steps, the approximate Gaussian count, and any honest caveats or shortcuts.

## What 3D Gaussian Splatting is (self-contained primer)

3DGS represents a scene as a cloud of anisotropic 3D Gaussian primitives. Each Gaussian has:

- A 3D position `(x, y, z)`.
- A rotation, usually stored as a unit quaternion `(qw, qx, qy, qz)`.
- A 3D scale `(sx, sy, sz)` (often optimized in log-space).
- An opacity `α ∈ [0, 1]`.
- A color, typically encoded as **spherical harmonics (SH)** coefficients so color can vary with view direction. Degree-0 SH is just RGB; higher degrees add view-dependent shading.

The canonical training pipeline:

1. **Pose estimation** — recover per-image camera intrinsics and extrinsics. Classic approach: COLMAP Structure-from-Motion. Modern pose-free alternatives: DUSt3R / MASt3R, or end-to-end models that skip explicit poses.
2. **Initialization** — seed an initial sparse point cloud (from SfM, learned dense matching, or random points in a bounding volume); convert each point to a small Gaussian.
3. **Differentiable tile-based rasterization** — project Gaussians into screen-space tiles, sort by depth, alpha-blend front-to-back. The whole rasterizer is differentiable, so per-pixel error backpropagates into the Gaussians' parameters.
4. **Photometric loss** — combine L1 and D-SSIM (typically `0.8·L1 + 0.2·DSSIM`) between rendered and reference images.
5. **Adaptive density control** — periodically clone Gaussians in under-reconstructed regions, split Gaussians that are too large, and prune near-zero-opacity Gaussians. Driven by view-space gradient magnitudes and opacity.
6. **Output** — the final scene is a `.ply` or `.splat` file that any 3DGS viewer can render.

Standard quality metrics on held-out views: **PSNR**, **SSIM**, **LPIPS**.

Reference: Kerbl, Kopanas, Leimkühler, Drettakis. *3D Gaussian Splatting for Real-Time Radiance Field Rendering*. SIGGRAPH 2023.

## Acceptable approaches

You decide what's actually achievable in this sandbox. Any of the following is a legitimate v1 attempt:

### A. Optimization-from-scratch in the browser
Implement (or wire up) a differentiable Gaussian rasterizer in **WebGPU compute shaders**, run a reduced training loop on the attached images, and render the result. The Rust+WGPU project [`ArthurBrussee/brush`](https://github.com/ArthurBrussee/brush) is a reference implementation that targets the browser via WASM. This is the hardest path and converging in browser time-budgets is non-trivial — be realistic about iteration counts and Gaussian counts.

### B. Feed-forward inference in the browser
Load a **pretrained sparse-view 3DGS model** in the browser, run inference on the attached images, and render the predicted Gaussians. Candidates from the research literature: NoPoSplat, Splatt3R, MASt3R-derived stereo models, AnySplat. Practical browser ML runtimes: [`onnxruntime-web`](https://onnxruntime.ai/docs/tutorials/web/), [`@huggingface/transformers`](https://github.com/huggingface/transformers.js). You may need to convert a model to ONNX or find an existing web-compatible export; if no suitable export is publicly hosted, say so and fall back to (C).

### C. Honest hybrid / approximation
If true 3DGS optimization or feed-forward inference isn't reachable in this sandbox, produce the **closest honest approximation** that still uses Gaussian-splat-style rendering. For example: estimate sparse geometry from local feature matching across the input images (or from monocular depth), seed a Gaussian point cloud, and render with a real splat renderer (positions and colors fixed; no gradient training). Clearly label this as an approximation in the on-screen text panel and explain what you skipped.

What is **not** acceptable: a baked screenshot, a hard-coded scene unrelated to the inputs, a triangle-mesh photogrammetry result rendered as a mesh, a NeRF, or any output that doesn't visibly use 3D Gaussian splats as the rendering primitive.

## Honesty clause

The on-screen text panel must accurately describe what your code actually does. Do not claim optimization-based 3DGS if you shipped a feed-forward approximation; do not claim feed-forward if you shipped a static scene. If you took a shortcut (e.g. fixed camera poses to a default circle, used a single image rather than all of them, skipped densification, used a pretrained model that wasn't trained on this kind of scene), say so plainly. A working honest approximation will score higher than a polished-looking fake.
