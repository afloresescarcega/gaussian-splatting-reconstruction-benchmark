## What 3D Gaussian Splatting is (primer)

3DGS represents a scene as a cloud of **anisotropic 3D Gaussian primitives**, each with:

- A 3D position `(x, y, z)`.
- A rotation, usually a unit quaternion `(qw, qx, qy, qz)`.
- A 3D scale `(sx, sy, sz)` (often log-space). Rotation + 3D scale define an anisotropic world-space 3×3 covariance — oriented ellipsoids, **not** screen-facing point sprites.
- An opacity `α ∈ [0, 1]`.
- Color, typically **spherical harmonics (SH)**; degree-0 SH is plain RGB.

Canonical pipeline:

1. **Pose estimation** — per-image intrinsics/extrinsics (classic: SfM such as COLMAP; pose-free alternatives: DUSt3R / MASt3R or end-to-end models).
2. **Initialization** — sparse point cloud (SfM, dense matching, or random in a bounding volume) → one small Gaussian per point.
3. **Differentiable tile-based rasterization** — project to screen tiles, depth sort, alpha-blend front-to-back; differentiable so per-pixel error backpropagates.
4. **Photometric loss** — `0.8·L1 + 0.2·D-SSIM` against the input images.
5. **Adaptive density control** — clone / split / prune Gaussians.
6. **Output** — a `.ply` / `.splat` any 3DGS viewer can render.

Reference: Kerbl et al., *3D Gaussian Splatting for Real-Time Radiance Field Rendering*, SIGGRAPH 2023.

## Approaches

What I actually want is close to the canonical pipeline: **estimate cameras from the images, initialize Gaussians, then refine them photometrically against the inputs.** A reduced version is fine — e.g. a few hundred optimization steps over ~10–50k Gaussians at low resolution, in WebGPU compute, WebGL, WASM, or even CPU with hand-derived gradients. The building blocks:

- **A. Optimization in the browser** — a differentiable Gaussian rasterizer and a training loop on the uploaded images. Reference: [`ArthurBrussee/brush`](https://github.com/ArthurBrussee/brush) (Rust+WGPU, runs in the browser via WASM).
- **B. Feed-forward inference in the browser** — a pretrained pose / pointmap / depth / sparse-view-3DGS model via `onnxruntime-web` or `@huggingface/transformers`. Check that a browser-loadable export of the model you pick actually exists and is a reasonable download before building around it. Model weights may be fetched from a public CDN / Hugging Face at runtime.
- **C. Geometric initialization** — feature matching → relative pose → triangulation, or depth → unproject → orient by local normal, producing anisotropic 3D Gaussians derived from the uploaded images at runtime.

A hybrid (B and/or C to get cameras + an initial cloud, then A to refine) is the expected shape. An initialization-only result is acceptable if refinement genuinely doesn't work out — say so plainly — but it is not the goal. Honesty still beats appearance: a working, honestly described pipeline beats a broken or faked one.

## What does NOT count

- Isotropic screen-facing point sprites with Gaussian alpha (the primitive must be an anisotropic 3D Gaussian).

- Implementation-notes claims without code: if the panel names feature matching, SfM, bundle adjustment, photo-consistency, monocular depth, SH optimization, etc., a function must actually do it.
