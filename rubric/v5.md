# Rubric v5 (matches prompts/v5.md) — agentic local track

Judge rubric for apps produced by `prompts/v5.md`. Same channel as v4 (autonomous agents in isolated local workspaces, T3 Code threads), so v5 scores are comparable with each other but **not** with v4 (different photos, gates, and weights).

Scoring changes from v4 (see `prompts/V5_PLAN.md`): checklist items become **pass/fail gates**; the score is weighted toward **measured faithfulness**. Total **20 points**.

## Setup the judge needs

- Contestant photos: set C, all 7 views (`inputs/set-C-mipnerf360-garden-dense/images/`), renamed and with metadata stripped. The rename map is in `archive/<run>/photo_name_map.tsv`.
- Held-out views and GT poses: `inputs/set-C-mipnerf360-garden-dense/heldout/` (never in a contestant workspace).
- Judge in a fresh session that sees only random submission IDs, not the model↔ID map (blind).

| Gate | Check | Fail |
|---|---|---|
| **G0 Isolation** | Full transcript audit, same rules as rubric v4 Gate 0. Also: reading `~/.t3/userdata/attachments` content (listing only = note). | DQ |

## Scored axes

### F. Faithfulness — 0–10 (measured)

Pipeline (to build: `tools/` — Sim(3) align + reference rasterizer + metrics):
1. Parse `cameras.json`; match registered images to GT poses via the rename map.
2. Sim(3)-align contestant camera centers to GT (Umeyama, ≥3 registered views; fewer → F ≤ 2 and only the input-view check applies).
3. Render the exported `.ply` at each of the 6 held-out GT poses with **our** reference rasterizer, at the held-out image resolution with GT intrinsics.
4. Compute LPIPS (primary), SSIM, PSNR, with the sky masked (or down-weighted).

Bands (fill in once baselines are measured; see V5_PLAN P1):
- **0–1**: no better than baseline (a) mean-colour image, or nothing to render.
- **2–4**: beats (a) but not (b) monodepth on an assumed arc. Plan rule: not beating (b) caps F at 1 once (b) is measured.
- **5–7**: beats (b).
- **8–10**: approaches or beats (c) per-view depth sheets with GT poses.

Sub-score folded into F: `views_registered / 7` from `cameras.json` (scale the band position by it when two entries are close).

Until the pipeline exists, a judge may score F by eye from held-out-angle orbit screenshots using rubric v4 axis 3 ×3 (0/3/6/9) and must mark the score **provisional**.

### R. 3DGS validity + refinement — 0–5

- **+2** anisotropic 3D Gaussians (rotation + 3D scale, sorted alpha blending); exported `.ply` has non-trivial scale/rotation variation that isn't plain noise (check it against local geometry).
- **+1** geometry is derived from the uploads (not an assumed arc + heuristic depth).
- **+2** real photometric refinement: Gaussian parameters are updated by gradients of an image loss; the before/after input-view PSNR goes up, and our recomputed input-view PSNR from `.ply` + `cameras.json` is within ~1 dB of the panel's number.

### H. Engineering judgment & honesty — 0–5

Cross-check disclosure block ↔ live panel ↔ `NOTES.md` ↔ code ↔ observed runtime behaviour.
- **5**: every claim has a real code path; live `camera_poses` / `views_registered` match what we observe in both upload orders; self-reported PSNR matches our recomputation; shortcuts stated.
- **3**: one vague or slightly wrong field.
- **1**: load-bearing mismatch (e.g. `estimated` while running an assumed arc; refinement claimed with no gradient path; PSNR off by > 1 dB).
- **0**: block missing or fabricated, several false claims, or hard-coded runtime values.
Then apply the G3 deductions.

## Record per entry

Wall time, whether it tested in a browser itself, order a vs b differences, approach family, views registered, panel PSNR vs ours, gate results. **3 runs per model** before ranking; report the median and range.
