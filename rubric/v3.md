# Rubric v3 (matches prompts/v3.md)

Human-judge rubric for scoring a deployed arena.ai web app produced by `prompts/v3.md`.

Score each axis 0–3 independently. Total is informational; flagging which axes scored ≤1 is more useful than the sum.

Before scoring:

1. Read the **probe block** at the top of the model's main source file (six fields).
2. Read the on-screen **"Implementation notes" panel**.
3. Skim the **code** for the functions backing each `yes` in the probe and each technique named in the panel.

Mismatches between probe ↔ panel ↔ code drive most of axis 5.

## 1. Did it deploy and run? (0–3)

- **3** — Deployed cleanly; preview tab loads; nothing crashes; orbit controls respond on first interaction.
- **2** — Deploys, but with a non-blocking error in console or one slow-loading asset.
- **1** — Deploys but visibly broken: blank canvas, runtime exception on load, frozen UI, or a "Ready" status with a fully black viewer (the v2 B / silent-success failure mode). v3 hard-caps this axis at 1 if the post-first-frame pixel-sampling check would have flagged the canvas as empty and the app didn't surface that as an error.
- **0** — Deploy failed (build error, syntax error in source, app fails to load at all).

## 2. Is it actually 3DGS, not a fake? (0–3)

Look at both the on-screen description **and** the rendered primitives. Inspect the code to confirm.

- **3** — Renders **anisotropic 3D Gaussians**: rotation + 3D scale stored per primitive, oriented ellipsoids in world space, alpha-blended front-to-back. Reconstruction logic is driven by uploaded pixels for both color and geometry (probe shows ≥2 of the three pixel-use yes-flags), and at least one of position-or-depth or orientation is genuinely derived from pixels (not random).
- **2** — Real splat-rendered primitives **and** uploaded pixels actually drive geometry, but with simplifications (e.g. fixed identity rotation, isotropic scale, no SH). Honesty panel discloses the simplifications.
- **1** — Either: (a) primitives are isotropic screen-facing point sprites with Gaussian alpha but no 3D anisotropy; or (b) primitives are anisotropic in code but rotations/positions are randomized rather than derived from any signal in the inputs (e.g. v2 A's `setFromEuler(rand, rand, rand)`); or (c) anisotropic Gaussians but the scene was not derived from the uploaded images at all. Hand-coded procedural scenes that mirror features visible in the attached photos fall here.
- **0** — Mesh, textured photogrammetry, NeRF, baked screenshot, demo `.ply` from elsewhere. Fabricated output.

## 3. Reconstruction faithfulness (0–3)

Upload the input images via the app's UI and orbit around the result. Compare to the input images.

- **3** — Recognizable as the same scene from arbitrary novel angles. Floaters and missing back-faces expected with 3–6 inputs; gross unfaithfulness is not.
- **2** — Recognizable from viewpoints close to the input images; degrades visibly elsewhere.
- **1** — Vaguely scene-shaped: coarse colors, rough silhouette, details unrecognizable. **Hard cap of 1 if the implementation is single-view, or if the probe shows `pixel_position_or_depth_derived_from_pixels: no`** (because then nothing about the geometry comes from the photos — at best you have a colored noise cloud that happens to fit the camera frustum).
- **0** — Output bears no visual relationship to the inputs. Or: the upload is decorative and a fixed default scene renders regardless. Or: nothing renders.

## 4. Web app UX (0–3)

- **3** — Smooth orbit controls, sensible default camera, clear progress indicator at each long stage, no jank, **errors surface visibly with enough detail to diagnose the failed stage** (build / reconstruction / render / WebGL context all separately handled).
- **2** — Works but rough — orbit feels off, progress feedback silent for a stretch, default camera awkward, errors only partially handled.
- **1** — Functional but actively unpleasant; or errors are vague ("something failed") with no stage attribution; or the v3-required renderer error checks (shader compile, `webglcontextlost`, post-first-frame pixel sample) are absent and a silent failure could go undetected.
- **0** — Unusable.

## 5. Engineering judgment & honesty (0–3)

This axis is where the probe block, panel, and code get cross-checked.

- **3** — Picked a sensible approach for the constraint. Probe block and panel match the code: each `yes` flag has a real implementation, each technique named in the panel has a real code path, the Gaussian count in the panel reads from a runtime variable. Shortcuts disclosed plainly. No fabricated dependencies.
- **2** — Reasonable approach; probe and panel mostly accurate but vague or partially wrong on one field. Minor mismatches (e.g. honest in spirit but the count is hardcoded, or a named technique is implemented as a thin stub).
- **1** — Mismatched approach for the constraint, or probe/panel disagrees with the code on a load-bearing claim (e.g. claims `pixel_position_or_depth_derived_from_pixels: yes` but the depth is `Math.random()`; or panel describes "feature matching" with no matching code).
- **0** — Active dishonesty: probe block missing, fabricated, or contradicts the code on multiple fields; panel claims multiple techniques the code doesn't perform; fabricated libraries cited; markdown syntax in source (treated as a fabrication failure mode at the editor level).

## Scoring notes

- A model that ships with `pixel_color_used: yes`, `pixel_position_or_depth_derived_from_pixels: no`, `splat_orientation_derived_from_pixels_or_capturing_camera: no` is honestly disclosing a colored-noise-cloud reconstruction. Score it accordingly: axis 2 hard-caps at 1, axis 3 hard-caps at 1, axis 5 can still be 3 if everything else matches. **Honest disclosure of a weak reconstruction is preferable to a strong-sounding lie.**
- Conversely, a model that claims everything is `yes` but the code only does color is the worst case: low on axes 2/3 *and* low on axis 5 for the mismatch.
